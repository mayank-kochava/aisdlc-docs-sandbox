| Entities + repositories (`Blend`, `BlendSource`, `CanonicalField`, `CanonicalMapping`, `JoinConfig`, `JoinKeyPair`, `UnionRowIdentity`, `UnionAggregationRule`, `MissingValueHandling`, `PartialFailurePolicy`, `BlendRunOutcome`, `ConnectorBlendDependency`) | New | H | 12 entity/repo pairs, mechanically similar to `Pipeline.kt` but real volume |
| `BlendController.kt` + `BlendHandler.kt` | New | M | CRUD + duplicate + list/search, mirrors `PipelineController.kt`'s `@Post`-per-action shape |
| `CanonicalMappingController.kt` + `CanonicalMappingHandler.kt` | New | M | Source-scoped, cross-blend blast radius; revision-based optimistic concurrency (FR-056) |
| `CompositionGraphValidator.kt` | New | H | Live `WITH RECURSIVE` for authoring-time checks + narrow `ConnectorBlendDependency` reverse-index maintenance |
| `BlendScheduler.kt` | New | H | Kochava-owned cron scheduler for blend-backed pipelines (no native Connection for the pull-and-combine leg) — new territory, no existing precedent to mirror closely |
| Staging writer (part of the concurrent-pull trigger path) | New | H | Writes each contributing source's pull as Parquet to `blend-staging/` GCS prefix |
| `airbyte-blend-combiner` module (`BlendCombineJob.kt`) | New | H | DuckDB via `httpfs`, reads staged Parquet, computes Union/Join, writes output to `blend-output/` GCS prefix + `BlendRunOutcome` |
| `BlendCombineJobPodFactory.kt` | New | M | New Fabric8 `PodBuilder` factory, `emptyDir sizeLimit: 30Gi`, its own `blend-combine-workload` taint/toleration (distinct from `ReplicationPodFactory`'s `airbyte-workload` — a separate node pool, not shared) |
| `BlendOutputController.kt` + `BlendOutputHandler.kt` | New | M | Serves a completed run's `blend-output/` file over HTTPS at `KOCHAVA_PUBLIC_API_URL`, for a `source-file` Source to read — reuses `CustomFileSourceController`/`CustomFileSourceHandler`'s "Kochava-hosted download URL, token-guarded, not Oathkeeper" pattern, streamed from GCS instead of a Postgres blob table (see `eng-research.md`'s output-leg decision for why the storage swap matters) |
| `BlendScheduler.kt` output-leg responsibility | New | M | After a combine run succeeds: create-or-reuse a `source-file` Source (`HTTPS: Public Web` mode, pointed at the `BlendOutputHandler` URL) + native Connection to the pipeline's real destination, then trigger that Connection's sync via the existing on-demand sync-trigger path — same mechanism the UI's manual-sync action already uses |
| `AlertConditionEvaluator` extension | Modify | L | Add `run_degraded` condition type alongside existing ones |
| `BlendAcceptanceTest.kt` | New | M | Happy-path: create blend, trigger combine, poll outcome, confirm the output-leg Connection's sync completes and lands records at the destination — following `SyncAcceptanceTest.kt`'s pattern |
