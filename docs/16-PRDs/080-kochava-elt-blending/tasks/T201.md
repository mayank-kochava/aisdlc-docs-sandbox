## Implementation Guide

1. Follow eng-plan, not the task text: local SSD is a pool-wide property and the existing `s-n4-std-8-airbyte` pool is shared by every other job type. In `ko-infrastructure/service/qa/platformmesh/greedy_goat.tf`, add a new dedicated node pool (eng-plan example name `s-n4-std-8-blend-combine`, Spot VMs, ~24 vCPU ceiling) and leave `s-n4-std-8-airbyte` untouched.
2. On the new pool only, set `local_ssd_ephemeral_storage_count = N`, where N is a literal integer. Get N from the SRE owner (an Open Item) and do not guess it. If it is not yet known, stop and ask rather than committing a placeholder.
3. Give the new pool a taint matching the `blend-combine-workload` key that eng-plan says `BlendCombineJobPodFactory.kt` tolerates. Record the final pool name and taint key in the PR description so the release.yaml task can reuse them exactly.
4. Use only `local_ssd_ephemeral_storage_count`. Do not use `local_ssd_count`, `local_ssd_ephemeral_count` or `local_nvme_ssd_count`; they would leave `emptyDir` on the boot disk.
5. Treat `modules/beta-private-cluster/cluster.tf` (module `terraform-google-modules/kubernetes-engine`, pinned `v41.0.1`) as read-only reference for re-confirming the field name. Do not edit it.
6. Keep the change QA-only, in its own issue/PR separate from any application-code task. Run the test command and attach `terraform plan` output to the PR.
