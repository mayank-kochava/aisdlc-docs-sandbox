### CA-2 — **Chosen generation home: `summary-worker-1-3` — PROD = 20 static replicas, no HPA**
`reporting/summary-worker/prod/summary-worker-1-3.yaml:38-61`
```yaml
spec:
  selector:
    matchLabels:
      app: summary-worker-1-3
  replicas: 20
  template:
    ...
      containers:
        - name: worker
          image: .../kochava/summary-report-cloud:1.13.6
          resources:
            limits:   { memory: "25000Mi", cpu: "2" }
            requests: { memory: "4500Mi",  cpu: "1" }
```
Observations:
- **Prod runs a fixed pool of 20 replicas.** Heavy per-pod footprint (up to 25 GB memory, 2 CPU limit).
- It is a **PubSub pull-subscription consumer**, not an HTTP endpoint: `PUBSUB_SUBSCRIPTION: "ko-p-restmeas-pss-summary-report-requests-1-3-worker"` (`reporting/summary-worker/prod/summary-worker-1-3.yaml:15`). Work (report requests) is fanned out across the 20 replicas by the subscription; running multiple replicas is intended and safe here — each pod pulls distinct messages.
- `MAX_ROWS_RETURNED: "2500000"` (line 26) → built to assemble large report datasets.

### CA-4 — No HPA / KEDA autoscaling attached to summary-worker (confirmed by exhaustion)
`reporting/summary-worker/prod/kustomization.yaml:6-11`
```yaml
resources:
- ../base/summary-worker-1-3.yaml
patches:
- path: ./summary-worker-1-3.yaml
- path: ./summary-worker-1-3-etc-secret.yaml
```
Observations:
- The prod and qa kustomizations reference only the base deployment + secrets. No HPA, no `ScaledObject`.
- Namespace-wide grep for `kind: ScaledObject`/`HorizontalPodAutoscaler` in `reporting/` returns matches **only** for `detail-worker` and `reporting-api` — **never `summary-worker`**. So summary-worker's parallelism is governed purely by the static `replicas` value, not by queue-depth autoscaling.

### CA-5 — Contrast precedent: a sibling report worker in the SAME namespace IS autoscaled (KEDA)
`reporting/detail-worker/prod/detail-worker-1-4-scaledobject.yaml:5-35`
```yaml
spec:
  scaleTargetRef:
    name: detail-worker-1-4
  minReplicaCount: 1
  maxReplicaCount: 50
  pollingInterval: 30
  cooldownPeriod: 28800     # 8 HOURS before scaling down (queries can run 7+ hours)
  ...
  triggers:
    - type: gcp-pubsub
      metadata:
        mode: "SubscriptionSize"
        value: "1"           # 1 message per pod
        subscriptionName: "projects/ko-p-restmeas-98fj/subscriptions/ko-p-restmeas-pss-detail-report-requests-1-4-worker"
```
Observation: `detail-worker` (the detail-report sibling of summary-worker, same restmeas project, same PubSub-request pattern) uses **KEDA queue-depth autoscaling, min 1 / max 50**. So the namespace has a ready precedent if the new feature's generation worker should autoscale on request volume rather than run a fixed pool — this is a real design option, not a hypothetical.

### CA-6 — Single-replica background/periodic tier precedent (same `netwrkcost` codebase family)
`netwrkcost/ingestion/base/scheduler.yaml:21-33`
```yaml
kind: Deployment
metadata:
  name: scheduler-deployment
spec:
  replicas: 1
  minReadySeconds: 4
```
`netwrkcost/ingestion/prod/scheduler.yaml:60-76`
```yaml
      containers:
        - name: scheduler
          image: .../kochava/cost-v2:v1.58.2
          command: ["/usr/local/bin/cost-v2", "scheduler"]
```
Observations:
- The `scheduler` is a **separate run-mode of one binary** (`cost-v2 scheduler`), deployed as its own Deployment at **`replicas: 1`** (set in base, **not** overridden in the prod overlay → prod inherits 1). It drives periodic job scheduling (`JOB_SCHEDULER_TOPIC`, `JOB_RETRY_DELAY: "60m"`), publishing jobs that the scaled worker pool then consumes.
- This is exactly the "deliberately single-replica background/periodic tier, split out from the horizontally-scaled worker pool" topology. **If the new weekly-cadence generation needs a periodic trigger/scheduler loop, this repo already demonstrates the right pattern: a separate single-replica scheduler Deployment distinct from the multi-replica consumer Deployment** — don't bolt a periodic loop onto a 20-replica pool, or it runs 20×.

### CA-7 — AaaS reporting output (attribution-as-a-service) is a different topology: synchronous HTTP, 3 replicas
`adsmeasurement/aaas-reporting/prod/aaas-reporting.yaml:12-49`
```yaml
kind: Deployment
metadata:
  name: &name aaas-reporting
spec:
  replicas: 3
  ...
      containers:
        - name: *name
          image: .../kochava/aaas-reporting:0.1.13
          env:
            - { name: LISTEN_ADDRESS, value: ":8080" }
            - { name: GCS_BUCKET, value: "aaas-reporting" }
            - { name: GCS_SIGNED_URL_CREDENTIAL_PATH, value: "/var/run/secrets/reporting-gcs/service-account.json" }
```
Observations: `aaas-reporting` (the KG cross-check's "attribution-as-a-service reporting output") is a **synchronous HTTP service** (`LISTEN_ADDRESS :8080`), **prod replicas: 3**, writing report artifacts to GCS bucket `aaas-reporting` and handing back **GCS signed URLs**. No HPA in its manifest. This is a different delivery model (request/response + signed-URL download) than summary-worker's async PubSub-consumer model — relevant if the "download button" flow wants a signed-URL handoff rather than a queued job.

## Confirmed / corrected assumptions

| Assumption (implied by the question) | What the manifests actually show |
|---|---|
| There's a service literally named "cloud-worker" | **No.** No `cloud-worker` app exists. The `-cloud` images are `summary-report-cloud` and `rollup-worker-cloud`, both built from `netwrkcost-api` and deployed under `reporting/` and `restricted-measurement/`. |
| The generation home might be a single-replica background tier today | **No — not for summary-worker.** Prod = **20 static replicas**, QA = 1. It is a multi-replica PubSub-consumer pool by design (work is partitioned across pods by the subscription). |
| It is HPA/KEDA autoscaled | **No for summary-worker** (verified by kustomization + namespace-wide grep). Its sibling `detail-worker` **is** KEDA-autoscaled (min 1 / max 50); `reporting-api` also uses ScaledObjects. |
| A single-replica periodic/background tier pattern exists to copy | **Yes** — `netwrkcost` `scheduler` (`replicas: 1`, separate `cost-v2 scheduler` run-mode) is the precedent for a deliberately-single-replica periodic tier split from the scaled worker pool. |

## Deploy-topology implications for the decision (grounded, not prescriptive)

- A new on-demand/weekly report-generation worker modeled on **summary-worker would be multi-replica and PubSub-driven, NOT single-replica** — and that's correct for *stateless request consumers*, where duplication across pods is safe because the subscription partitions messages.
- The **single-replica concern applies only to a periodic/scheduler trigger** (if the "weekly generation cadence" FR-001 needs a timer loop). The repo's answer to that is **CA-6**: run the scheduler as its own `replicas: 1` Deployment (separate run-mode), separate from the scaled consumer pool — so the periodic loop fires once, not once-per-replica.
- If request volume for the new report is bursty/unpredictable, **CA-5 (`detail-worker` KEDA ScaledObject)** is the in-namespace template for queue-depth autoscaling instead of a fixed 20-replica pool.
