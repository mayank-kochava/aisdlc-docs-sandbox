# T002: Token-bucket limiter with defaults

## In short

Builds the core rate limiter. It hands out a limited number of requests per second, lets short bursts through and refills over time. The default limits come from the owner, so the agent has to ask for them rather than guess.

## User Story

**US1**

**Acceptance:**
- FR-1: `ratelimit.New(rate float64, burst int, clock Clock) *Limiter` creates a limiter that refills `rate` tokens per second up to `burst` tokens; it starts full.
- FR-2: `Allow() bool` takes one token if available and returns true; otherwise returns false without blocking.
- FR-3: Refill is computed lazily from elapsed clock time on each call (no goroutines, no timers). Fractional tokens carry over between calls.
- FR-4: Defaults: `rate <= 0` or `burst <= 0` use a default rate and burst chosen by the owner (Mayank). The numbers are **not written in this document**; the coding agent must ask the owner for them and must not guess.
- FR-5: `Tokens() float64` returns the current token count after refill. Safe for concurrent use.

## Implementation Guide

1. Before writing the default values, ask the owner (Mayank) for the default rate and burst. Do not guess or invent numbers; if no answer is available, report the task as blocked on FR-4.
2. Create `ratelimit/limiter.go` with `Limiter` holding rate, burst, tokens (float64), last (time.Time), a `sync.Mutex` and a `Clock`. Use the standard library only and make no `go.mod` changes.
3. Implement `New(rate float64, burst int, clock Clock) *Limiter`. When `rate <= 0` or `burst <= 0`, substitute the owner-provided default for that argument, defined in one place in `limiter.go`. When `clock` is nil, use `SystemClock()`. The limiter starts full, with tokens = burst and last = clock.Now().
4. Add a lock-held helper that refills lazily to `min(burst, tokens + elapsed*rate)` using the clock, with no goroutines or timers. Fractional tokens carry over.
5. Implement `Allow() bool`, which refills, then spends one token and returns true if tokens >= 1, otherwise returns false without blocking. Implement `Tokens() float64`, which refills and returns the count. Both take the mutex.
6. Write table-driven tests in `ratelimit/limiter_test.go` using `FakeClock`: start-full, drain, partial refill, burst cap, invalid-argument handling and a concurrent `Allow`/`Tokens` test. Run with `-race`. Do not assert specific default numbers unless the owner has supplied them.

## Acceptance Criteria

- WHEN `New(rate, burst, clock)` is called with valid arguments THE SYSTEM SHALL return a limiter that starts full, so `Tokens()` equals `burst`. [FR-1]
- WHEN `Allow()` is called THE SYSTEM SHALL return true and consume one token if at least one is available, and otherwise return false without blocking. [FR-2]
- WHEN the fake clock advances between calls THE SYSTEM SHALL refill lazily to `min(burst, tokens + elapsed*rate)` and carry fractional tokens over. [FR-3]
- WHEN `New` is called with `rate <= 0` or `burst <= 0` (for example `New(0, 5, clock)`, `New(-1, 0, clock)`, `New(0, -1, clock)`) THE SYSTEM SHALL not panic and SHALL return a limiter that keeps any valid argument (`New(0, 5, clock).Tokens()` equals 5) and whose first `Allow()` returns true. [FR-4]
- WHEN `Allow()` and `Tokens()` are called from multiple goroutines THE SYSTEM SHALL pass `go test -race ./ratelimit/...` and return the post-refill count from `Tokens()`. [FR-5]
- Existing tests pass
- New functionality has test coverage
- Code follows repository conventions (see CLAUDE.md)
