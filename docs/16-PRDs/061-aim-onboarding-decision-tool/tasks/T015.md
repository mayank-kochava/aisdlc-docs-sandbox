## Steps

1. Create `OnboardingTimelineService.cs` and `OnboardingTimelineController.cs` with `PUT /{id}/timeline`. Start after T007.
2. Accept milestone status changes, a new-date delay stored as `DelayedToDate`, and notes.
3. Recompute the cascade to downstream milestones as a pure function so it is easy to unit test. Return 400 on a bad date.
4. Append one change-log entry per edit, with `UserEmail` stamped server-side from the session email (`x-user-id`).
5. Allow both client and CSM callers; do not gate on `IsAsAdmin`.
6. Timeline edits happen after approval. Confirm they are not blocked by the approved-session 409 in `ReplaceAsync`, and report it if the current data-layer API forces that.

## Acceptance Criteria

- [ ] Status, `DelayedToDate` and notes edits persist on the milestone.
- [ ] A malformed date returns 400.
- [ ] A delay cascades to the dependent milestones.
- [ ] Each edit adds exactly one `ChangeLog` entry whose `UserEmail` is the server-stamped session email.
- [ ] Both an advertiser user and a CSM can call it, including after the session is approved.
