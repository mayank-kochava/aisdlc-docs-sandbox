## Summary
For Amazon Ads SAN (13954) conversions, Amazon-derived fields are masked in every row-level output when the claim isn't `UNRESTRICTED`. Row-level outputs are Query reports, Detail reports, exports, network postbacks and CAP. Aggregates keep full breakdowns.
Design: **decide upstream, redact by config.**
- **watson** (Amazon module only) makes the per-conversion decision and sets a **generic** claim flag `row_level_restricted: true`. All Amazon knowledge stays in watson.
- **soccer-v2** gets a generic, config-driven option: a network config with `require_restriction_flag` applies its keypaths only to flagged conversions. No partner names in soccer.
- **Control** (network postbacks + CAP) honors the same flag and option in its existing sanitization-api keypath path.
- **Detail workers** (MySQL) apply the existing `report_filtering` column filter per row when the row's claim carries the flag.
- **Aggregate readers** read `unredacted_*` for 13954 rows inside the config window, using the Aggregated Insights config-CTE + UNION ALL pattern.
- **The Amazon field list is data:** `keypath_sanitization` rows (recipients `reporting`, `postback`) plus a `report_filtering` row, frozen from real QA payloads.
- **One switch:** `AMAZON_ADS_EGE_ENFORCE_FROM` on watson. Every other deploy is inert until it's set.

## Implementation Guide

1. Precondition: the watson eligibility change (`row_level_restricted` flag in `buildMatchObj` and mock field `amazonads_event_grain_eligibility` in the `reconcile.go` mock block) must be deployed to QA watson. This task's depends_on is empty, so add that dependency. Confirm the watson tests pass first (test_cmd).
2. Set `AMAZON_ADS_EGE_ENFORCE_FROM` on QA watson only, to a time before the capture. Run the QA capture job named in the eng-plan rollout (its location is not given in this task, so confirm it there). Cover install, re-engagement and event conversions, each with mock values `RESTRICTED`, `UNRESTRICTED` and missing.
3. For each of the 9 combinations, record whether the stored claim carries `"row_level_restricted":true`. Then record pass or fail for each output path: Query report, Detail report, export, network postback and CAP.
4. From the real QA payloads, list every Amazon-sourced keypath. For each, record its leaf type (string, numeric, timestamp, or repeated such as `san_claims`) and which recipients need it (`reporting`, `postback`, `report_filtering`).
5. Freeze that table as the canonical list and attach the capture output to the ticket. T102 and T103 consume this list, and T1001 can use the leaf types for masking.
